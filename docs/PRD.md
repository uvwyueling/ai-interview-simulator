## 1. 产品概述

### 1.1 一句话定义
Echo Interview 是一款面向求职者的 **AI 模拟面试官**——上传简历与岗位 JD，AI 即可生成贴合背景的面试题，通过语音作答与**动态追问**还原真实面试压力，并产出可视化的多维能力评估报告。

### 1.2 产品愿景
> 让每一位求职者，在走进真实面试间之前，都已经历过一场"几乎真实"的面试。

市面上的面试准备工具多停留在"题库背诵"层面——给一堆问题让用户自己练。但真实面试的核心难点不是"答得出第一个问题"，而是**面试官根据你的回答层层追问**时，你能否守住技术深度、保持表达清晰。Echo Interview 用 LLM 复刻了这一"追问"机制，这是它区别于传统题库类产品的根本立足点。

### 1.3 名称释义
"Echo（回声）"——你说出的每一句回答，都会被 AI 接住、反射、并追问。面试不是单向问答，而是一场双向回声。

## 2. 背景与问题陈述

### 2.1 用户面临的真实痛点

| # | 痛点 | 现状描述 |
|---|---|---|
| P1 | **缺乏真实压力环境** | 对着题库自问自答，没有"被追问到答不上来"的紧张感，上了真考场就慌 |
| P2 | **不知道自己答得好不好** | 练完没有反馈，不清楚是技术深度不够、还是表达逻辑混乱 |
| P3 | **题目不贴合自身背景** | 通用题库与个人简历、目标岗位脱节，练了用不上 |
| P4 | **找真人模拟成本高** | 约学长、找付费教练，时间难协调、价格不低、且质量参差 |
| P5 | **语言表达难以自检** | 面试是"说"出来的，但用户很难在事后客观回看自己"说"的内容与节奏 |

### 2.2 市场机会
- 应届毕业生 + 社招跳槽人群，每年存在巨大的、周期性的、刚性的面试准备需求。
- LLM 成本快速下降，使"个性化、可追问、即时反馈"的模拟面试在经济上首次变得可行。
- 语音转写（Web Speech API）+ 大模型，使"开口练习"这一最接近真实面试的形态可以在纯浏览器端实现，零安装门槛。

## 3. 目标用户

### 3.1 核心用户画像

**画像 A · 应届求职者「小张」**
- 计算机相关专业应届硕士，投递前端/后端/算法岗。
- 简历有项目和实习，但**没经历过几次真实面试**，对追问毫无准备。
- 诉求：在投递高峰前，低成本地反复练习，建立"被追问"的肌肉记忆。

**画像 B · 社招跳槽者「老李」**
- 3-5 年经验工程师，准备跳槽到更高级别岗位。
- 痛点是**很久没面试，手生**；且目标岗位 JD 要求与现有经验有 gap，需针对性查漏补缺。
- 诉求：针对目标 JD 做定向模拟，提前暴露薄弱环节。

### 3.2 次要 / 关联角色
- **HR / 招聘方（演示受众）**：通过 Demo 模式快速理解产品价值，评估是否引入团队招聘流程。（当前产品中以"示例数据预览"形态服务该角色）
- ⚪️ **职业教练 / 高校就业中心**：未来可能的 B 端分发渠道。

## 4. 产品目标与成功指标

### 4.1 北极星指标
**完成一次完整面试（含至少一次追问）并查看反馈报告的用户数。**
> 选择理由：它同时验证了核心价值链路（生成→追问→反馈）的完整跑通，是用户真正获得价值的最小信号。

### 4.2 关键指标（KPI）

| 维度 | 指标 | 说明 |
|---|---|---|
| 激活 | 输入完成率 | 进入应用 → 成功生成题目的转化率 |
| 核心体验 | 面试完成率 | 开始面试 → 看到反馈报告的转化率 |
| 深度 | 平均追问轮次 | 衡量"追问"机制是否真正被触发、体验是否真实 |
| 价值交付 | 报告导出率 | 查看反馈 → 导出 PDF 的比例（强价值认可信号） |
| 留存 | 二次面试率 | "开启新一轮面试"的点击与回访 |
| 成本 | 单场面试 LLM 成本 | 控制在可持续区间（当前约 $0.17/场，详见 §9.3） |

## 5. 用户流程与信息架构

### 5.1 核心三步流程

```
┌─────────────┐      ┌──────────────────────────┐      ┌─────────────┐
│ Step 1 输入  │ ───► │ Step 2 面试（含动态追问）   │ ───► │ Step 3 反馈  │
│ 简历 + JD    │      │ 主问题 → 答 → 判断 → 追问/进 │      │ 评分 + 报告  │
└─────────────┘      └──────────────────────────┘      └─────────────┘
```

### 5.2 面试环节的追问状态机（产品核心逻辑）

```
        生成 3 道主问题
              │
              ▼
        ┌───────────┐
        │  主问题 Qn  │◄──────────────┐
        └───────────┘                │
              │ 用户作答 An            │
              ▼                       │
        ┌───────────┐                │
        │ AI 判断     │                │ 生成追问 Qn.x
        │ 是否追问？   │                │（最多 3 次）
        └───────────┘                │
          │        │                  │
       否 │        │ 是               │
          │        └──────────────────┘
          ▼
   还有下一主问题？──是──► 进入 Q(n+1)
          │
          否
          ▼
      进入反馈环节
```

### 5.3 状态持久化
🟢 全程状态写入浏览器 `sessionStorage`，刷新页面不丢失进度（详见 §6.5）。

## 6. 功能需求详述

### 6.1 模块一：资料输入（InputStep） 🟢

**目标**：让用户用最低成本把"我是谁 + 我要应聘什么"输入系统。

| ID | 需求 | 状态 | 说明 |
|---|---|---|---|
| F1.1 | 简历文本输入 | 🟢 | 支持直接粘贴文本 |
| F1.2 | 简历文件解析 | 🟢 | 支持 `.txt`（FileReader）、`.docx`（mammoth.js 浏览器端解析） |
| F1.3 | PDF 友好降级 | 🟢 | 暂不支持 PDF 解析，提示用户复制文字粘贴（避免白屏报错） |
| F1.4 | 拖拽上传 | 🟢 | 支持拖拽文件到上传区 |
| F1.5 | JD 输入 | 🟢 | 文本粘贴 |
| F1.6 | 一键填充示例 | 🟢 | 简历 / JD 各有"试用示例"按钮，降低体验门槛 |
| F1.7 | 输入校验 | 🟢 | 简历与 JD 均需 ≥ 20 字方可生成 |
| F1.8 | Demo 快速通道 | 🟢 | 当简历与 JD 均为未修改的示例数据时，跳过 API、本地随机抽题（零成本演示） |
| F1.9 | PDF 在线解析 | 🟡 | 接入 pdf.js 真正解析 PDF 文本 |

**错误场景处理**：文件格式不支持、解析失败、文本过短——均包装为友好中文提示，不暴露原始错误。

---

### 6.2 模块二：题目生成（/api/generate-questions） 🟢

**目标**：基于简历与 JD，生成 3 道有"追问延展空间"的主问题。

| ID | 需求 | 状态 | 说明 |
|---|---|---|---|
| F2.1 | 生成 3 道主问题 | 🟢 | 由"5 道固定题"改版为"3 主问题 + 动态追问"（v0.2.0） |
| F2.2 | 题目结构化分布 | 🟢 | Q1 项目经历 / Q2 系统设计或技术深度 / Q3 行为或岗位匹配 |
| F2.3 | 分类与难度标注 | 🟢 | category（5 类）+ difficulty（easy/medium/hard） |
| F2.4 | Zod 输出校验 | 🟢 | 严格校验 LLM 返回的 JSON 结构，长度必须为 3 |
| F2.5 | 失败重试 | 🟢 | 最多 3 次，递增退避（600ms × 次数） |
| F2.6 | 模型选择 | 🟢 | 使用 `claude-sonnet-4-6`（质量关键，每场仅调用 1 次） |

---

### 6.3 模块三：面试作答与动态追问（InterviewStep + /api/generate-followup） 🟢 ★核心★

**目标**：复刻真实面试的"追问"压力，这是产品的核心差异点。

#### 6.3.1 语音作答

| ID | 需求 | 状态 | 说明 |
|---|---|---|---|
| F3.1 | 实时语音转文字 | 🟢 | Web Speech API，中文（zh-CN），录音时实时显示 interim 结果 |
| F3.2 | 文字编辑兜底 | 🟢 | 停止录音后转为可编辑 textarea，允许手动修正识别错误 |
| F3.3 | 浏览器兼容提示 | 🟢 | Safari/Firefox 不支持时进入即显示横幅，引导切换 Chrome 或直接打字 |
| F3.4 | 思考时间计时 | 🟢 | 记录"问题出现 → 首次开始作答"的思考时长 |
| F3.5 | 作答时长 / 字数 / 语速统计 | 🟢 | 实时展示，辅助用户自检表达节奏 |

#### 6.3.2 动态追问（核心逻辑）

| ID | 需求 | 状态 | 说明 |
|---|---|---|---|
| F3.6 | AI 判断是否追问 | 🟢 | 每次作答后，LLM 以"资深面试官 + HRBP"视角判断回答是否到位 |
| F3.7 | 追问触发条件 | 🟢 | 技术细节缺失 / 缺少量化结果 / 过于宏观 / 疑似知识盲区 |
| F3.8 | 追问上限 | 🟢 | 每道主问题**最多 3 次追问**（硬上限） |
| F3.9 | "AI 判断中"加载态 | 🟢 | 判断期间显示专属动画，避免用户误以为卡死 |
| F3.10 | 对话历史展示 | 🟢 | 当前主问题下的所有问答轮次可见、可展开全文 |
| F3.11 | Demo 模式跳过追问 | 🟢 | 演示模式每题答一次直接进下一题（零 API 消耗） |
| F3.12 | 容错降级 | 🟢 | 追问 API 失败 / 限流时，安全降级为"不追问、进入下一题" |

#### 6.3.3 进度与导航
🟢 顶部进度条显示"主题 N / 共 3 题"；追问以独立徽标标识（"追问 1/2/3"）。

**目标**：把整场对话转化为可读、可信、可带走的能力诊断。

| ID | 需求 | 状态 | 说明 |
|---|---|---|---|
| F4.1 | 按主问题综合评分 | 🟢 | 每道主问题的完整追问链作为整体评估（非逐轮打分） |

| F4.3 | 能力雷达图 | 🟢 | SVG 雷达图可视化五维表现 vs 满分基准 |
| F4.4 | 维度详情 | 🟢 | 每维度 2-3 条**援引回答原文/简历**的具体证据，禁止空泛套话（v0.3.0） |

| F4.7 | 跨题汇总 Tab | 🟢 | 多题完成后默认展示"汇总"页，聚合五维均分与去重后的优缺点（v0.3.0） |

## 7. 非功能需求

### 7.1 设计规范 🟢
- 主色 Indigo-600，辅色 Slate-50；圆角 rounded-lg；标题 font-semibold。
- 系统默认无衬线字体；最大内容宽度受控（max-w-4xl / 1240px 栅格）。

### 7.2 代码质量红线 🟢
1. 所有变量必须有 TypeScript 类型（防运行时崩溃）。
2. 所有 API 调用必须有 try-catch + loading/error UI（防白屏）。
3. 所有 AI 输出必须用 Zod 验证（防 JSON 解析失败）。

### 7.3 兼容性
- 🟢 语音功能：仅 Chrome 系完整支持（Web Speech API 限制）；Safari/Firefox 降级为打字输入并显式提示。
- 🟡 移动端适配：当前桌面优先，移动端布局待优化。

### 7.4 性能
- 🟢 反馈请求错峰发起，规避限流。
- 🟢 报告导出零额外依赖，不增加包体。

## 9. 技术架构与成本

### 9.1 技术栈 🟢
- 前端：Next.js 14（App Router）+ React + TypeScript + Tailwind + shadcn/ui
- 可视化：自研 SVG 雷达图
- 语音：Web Speech API
- AI：Next.js API Routes + Claude API（Anthropic SDK）

### 9.2 混合模型策略 🟢（v0.3.3）
集中配置于 `src/lib/models.ts`，按任务复杂度分级：

| 路由 | 模型 | 理由 |
|---|---|---|
| generate-followup | `claude-haiku-4-5` | 高频、二选一判断、速度优先 |
| generate-questions | `claude-sonnet-4-6` | 每场 1 次、需深读简历 JD |
| generate-feedback | `claude-sonnet-4-6` | 产品核心价值、需精准援引证据 |

### 9.3 单场成本（最坏情况估算）

| 环节 | 次数 | 模型 | 小计 |
|---|---|---|---|
| 题目生成 | 1 | sonnet | ~$0.010 |
| 追问判断 | ≤9 | haiku | ~$0.027 |
| 反馈生成 | 3 | sonnet | ~$0.135 |
| **合计** | | | **~$0.172 / 场** |

> 成本可持续。如需进一步降本，优先方向：①提示词缓存（复用固定 System Prompt）②追问历史摘要压缩（详见 §11 路线图）。

## 10. 竞品与差异化

| 类型 | 代表 | 局限 | Echo 的差异 |
|---|---|---|---|
| 静态题库 | 各类"面试题大全" | 无反馈、无追问、不个性化 | 个性化生成 + 动态追问 + 即时评分 |
| 真人模拟 | 付费教练 / 约学长 | 成本高、难约、质量不稳定 | 零成本、随时可用、标准稳定 |
| 通用 AI 对话 | 直接用 ChatGPT 问 | 无结构化评分、无语音、无报告 | 结构化五维评估 + 语音 + 可带走的 PDF 报告 |

**核心壁垒**：把"追问"做成产品级的状态机与判断逻辑（而非简单多轮对话），并配以"援引原文"的可信反馈——这是把"AI 玩具"做成"训练工具"的关键。

## 11. 范围界定与路线图

### 11.1 当前已交付（v0.3.5） 🟢
完整跑通"输入 → 生成 → 语音作答 → 动态追问 → 多维反馈 → PDF 导出"主链路，含状态持久化、Demo 模式、混合模型成本优化。

### 11.2 近期规划 🟡

| 优先级 | 事项 | 价值 |
|---|---|---|
| P0 | 移动端适配 | 扩大可用场景，移动端是高频练习场景 |
| P0 | 隐私声明文案 | 消除用户对简历数据的顾虑，提升输入转化 |

| P1 | 提示词缓存降本 | 复用固定 System Prompt，降低 feedback 成本 |
| P2 | 二次面试针对性出题 | 基于上一轮薄弱维度定向出题，形成训练闭环 |

## 13. 开放问题

1. **追问质量如何量化评估**？目前依赖 LLM 自判断，缺少"追问是否真的有价值"的客观度量——是否需要引入用户对追问的"有用/无用"反馈？
2. **是否需要账号体系**？无账号降低了使用门槛，但也丢失了留存与进步追踪。需结合北极星指标的实际表现决策。
3. **Demo 模式与真实模式的边界**——HR 演示场景与真实求职者场景的需求是否会逐渐分化为两类产品？
4. **反馈的"严格度"**——AI 打分应偏鼓励还是偏严苛？不同用户群（应届 vs 社招）可能期望不同。
